# 决赛审查、演示脚本与答辩口径

## 1. 文档结论

本文以《核心项目审查与决赛冲刺优化计划》为批准基线，结合当前工作区已有实现整理。状态只表示代码中已经存在或本轮改动中已经落地的事实，不把计划项写成已完成项。

当前产品已经形成可演示的主闭环：浏览器插件采集跨平台 AI 对话，显式推送到本地软件，经智能抽取与用户确认沉淀为知识图谱，再分别进入 Study 的复习闭环和 Work 的行动、风险与报告闭环。

决赛叙事统一为：

> 让散落在多个 AI 平台中的对话，不再结束于聊天窗口，而是沉淀成可复习、可追踪、可行动、可交付的个人知识资产。

当前最有竞争力的不是单一图谱、RAG 或动画，而是“跨平台采集 → 结构化 → 人工确认 → 图谱 → 主动复习/行动/报告”的完整链路。现场应优先证明该链路真实可用，不应扩展到尚未完成的公网、多用户或实时情报叙事。

## 2. 审查范围与状态定义

本次只审查两个核心工程：

- `knowledge-work-assistant`：Electron + React 软件端与 FastAPI 后端。
- `web-ai-chat-collector`：Chrome MV3 对话采集插件。

状态定义：

- **已完成**：当前代码或测试中已有明确实现证据，可进入回归和彩排。
- **部分完成**：关键路径已落地，但计划中的完整边界、迁移、测试或体验尚未闭合。
- **遗留**：当前未发现对应实现，或仍需真实环境验证，不能在答辩中按已完成承诺。

## 3. 架构与数据流

```text
DeepSeek / 千问 / 豆包 / Kimi / 复旦 / 元宝
                    │
                    ▼
Chrome 插件：DOM / 网络适配器采集
                    │
                    ├── IndexedDB 本地保存
                    └── 用户显式推送 HTTP
                              │
                              ▼
FastAPI /api/plugin/conversations（127.0.0.1:8788）
                    │
                    ├── 平台校验、幂等去重
                    ├── SQLite Observation
                    └── WebSocket 到达通知
                              │
                              ▼
React / Electron：候选抽取与人工确认
                    │
                    ▼
SQLite Knowledge Graph
             ┌──────────────┴──────────────┐
             ▼                             ▼
Study：推荐、测验、费曼反馈      Work：对象、承诺、风险、问答、报告
```

关键边界：

- 插件采集记录默认保存在浏览器 IndexedDB；只有用户启用并执行本地推送后才进入软件端。
- 软件端业务数据默认保存在本机 SQLite，后端固定监听 `127.0.0.1:8788`，当前定位是单机本地 Demo。
- 需要 LLM 的抽取、问答、详情和报告会把对应上下文发送到用户配置的模型端点；项目不提供“数据永不离开设备”的绝对承诺。
- API Key 由用户配置；软件端已具备加密存储路径，但演示时不展示、不朗读、不记录任何真实凭据。
- 当前不具备公网多用户隔离能力，也不应直接作为企业公网服务部署。

## 6. 180 秒演示脚本

### 6.1 演示前固定状态

- 后端运行于 `127.0.0.1:8788`，前端运行于 `5174`，Chrome 扩展已重新加载并登录目标 AI 平台。
- 窗口固定为 1280×820 或 1440×900；关闭系统通知、开发者工具和无关标签页。
- 默认使用彩排最稳定的主题，Study 与 Work 图谱均已有预置数据，且没有真实 API Key 出现在屏幕上。
- 准备一段已验证的 Study 对话和一段已验证的 Work 会议纪要；两段输入保持不变。
- 正常网络、慢网、断网分别完成 3 次彩排；任何在线步骤等待超过 5 秒，立即执行降级脚本。

### 6.2 分秒动作与口播

| 时间 | 屏幕动作 | 建议口播 | 成功标志 |
| --- | --- | --- | --- |
| 0–20 秒 | 在 AI 平台快速切换两段历史对话，再打开插件 | “我们每天在不同 AI 平台获得很多高质量答案，但问完以后，它们通常就沉在聊天记录里。真正的问题不是没有答案，而是答案没有变成之后能复习、能跟进、能交付的资产。” | 评委先理解“AI 对话沉没”问题 |
| 20–50 秒 | 插件采集当前对话并推送到本地软件；切回软件查看到达通知或待处理记录 | “插件把已经发生的对话接住，先保存在浏览器本地；只有用户显式推送，才进入本机软件。这里不是自动替用户做决定，而是把原始对话作为可追溯 Observation 保存下来。” | 软件端出现到达反馈或待处理记录 |
| 50–90 秒 | 打开待处理内容，运行候选抽取，勾选候选并确认入图，展示图谱增长 | “Agent 先把对话拆成候选知识点和关系，用户确认后才进入图谱。我们刻意保留这一步，因为可信的个人知识系统需要来源和确认，而不是让模型静默改写用户资产。” | 至少一个节点与一条关系进入图谱 |
| 90–125 秒 | 切 Study，打开推荐卡，展示推荐理由，进入费曼题并展示反馈 | “沉淀不是终点。Study 模式根据复习记录和错误情况告诉我现在该复习什么，再用费曼题检验我是否真的理解。普通 RAG 解决找得到，我们继续解决什么时候该复习、是否真正掌握。” | 推荐理由、题目和反馈三者至少展示两项 |
| 125–160 秒 | 切 Work，打开预置会议纪要对应图谱，展示关键人、承诺、依赖、风险，再打开已生成周报 | “同一个知识资产引擎在 Work 模式把会议纪要转成关键人、承诺、依赖和风险，并汇总成可交付的周报。Study 和 Work 不是两个产品，而是同一份个人上下文的学习闭环与行动闭环。” | 图谱中有工作对象与关系，报告可见 |
| 160–180 秒 | 回到统一图谱或推荐首页，停在来源、关系和行动结果同时可见的画面 | “我们的目标不是再做一个聊天框，也不是再做一个笔记工具，而是让每次 AI 对话都留在用户身上，从一次回答，变成之后持续复习、跟进和交付的个人知识资产。” | 最终画面稳定，产品价值一句话收束 |

### 6.3 五秒降级脚本

任何关键在线步骤超过 5 秒，不继续等待，不反复点击：

1. 口播：“现场模型响应受到网络影响，我切换到同一输入预先生成的结果，数据来源和处理步骤保持一致。”
2. 取消当前流式请求，切换到预置 Study 或 Work 图谱。
3. 从“候选确认后的图谱结果”继续演示，不伪装为刚刚实时生成。
4. 若插件推送失败，展示插件本地已保存记录，再切软件端已有 Observation，说明本地软件未连接时数据不会丢失，但本次推送需重试。
5. 若 WebSocket 异常，刷新软件端一次；仍失败则直接进入预置图谱，不在台上排查设置、端口或 API Key。

## 7. 答辩口径

### 7.1 一句话定位

“这是一个把跨平台 AI 对话转化为个人知识资产的本地知识工作台：插件负责接住对话，Agent 负责结构化，用户负责确认，Study 和 Work 负责让知识继续产生复习、行动与交付。”

### 7.2 与 Obsidian、Notion 的区别

推荐回答：

“Obsidian 和 Notion 很强，但核心前提是用户主动整理。我们接住的是已经发生、最容易沉没的 AI 对话，并继续把它转成候选知识、关系、复习任务、承诺、风险和报告。我们不是替代所有笔记工具，而是补齐 AI 对话到可行动知识资产之间的自动化入口。”

避免回答：

- “我们全面替代 Notion 或 Obsidian。”
- “完全不需要用户整理。”

### 7.3 与普通 RAG 的区别

推荐回答：

“RAG 主要解决过去内容能不能被找回来。我们在检索之外保留来源、结构和用户确认，并继续回答三个问题：现在该复习什么、现在该跟进什么、现在能交付什么。RAG 是底层能力之一，不是产品终点。”

### 7.4 为什么不全自动入图

推荐回答：

“因为个人知识与工作承诺都具有高语义风险。模型适合提出候选，但不应静默替用户修改长期资产。候选确认、Plan/Build 和高风险工具确认构成可信 Agent 的控制面，这是产品设计，不是模型能力不足。”

### 7.5 Study 和 Work 是否过于分散

推荐回答：

“两种模式共享同一条采集、结构化、确认和图谱链路，只是在资产产生后的闭环不同：Study 关注理解与复习，Work 关注承诺、风险和交付。统一对象是用户的 AI 对话与个人上下文，统一价值是让它持续产生结果。”

### 7.6 隐私与数据流向

推荐回答：

“插件原始数据默认保存在 IndexedDB，软件端数据默认保存在本机 SQLite，推送由用户显式触发，服务只监听 loopback。需要模型处理时，请求会发送到用户自行配置的 LLM 端点，所以我们不会笼统声称所有数据永不离开设备。当前是单机本地 Demo，不宣称已经满足公网企业部署要求。”

若追问鉴权：

“当前 loopback 部署降低了外部攻击面，但插件与软件的本地配对 token 仍是遗留加固项；在它完成前，我们不会把当前方案包装成完整的公网或企业鉴权。”

### 7.7 数据是否自动建图

推荐回答：

“插件推送后先形成原始 Observation；Agent 自动生成候选，用户确认后才写入正式图谱。准确口径是‘自动采集、智能抽取、用户确认入图’，不是‘推送后全自动建图’。”

### 7.8 行业风口是否实时

推荐回答：

“当前输出是基于用户现有 Work 图谱的机会假设，用于帮助用户发现关系和行动方向，不是实时市场情报。实时外部数据源、引用追踪和时效校验属于进入 20 强后的路线。”

### 7.9 支持多少平台

推荐回答：

“当前代码覆盖 DeepSeek、千问、复旦、豆包、Kimi 和元宝等平台，但不同平台受 DOM、协议和登录态变化影响。决赛只现场承诺已经彩排通过的平台，不把适配器数量等同于永久兼容保证。”

### 7.10 为什么使用图谱

推荐回答：

“图谱不是为了视觉效果，而是为了显式表达来源、概念、人物、承诺、风险和依赖之间的关系。它让推荐理由、复习路径和工作报告有结构化依据。节点规模很大时会考虑 Canvas 或其他存储与渲染方案，但当前单机个人知识场景优先保证闭环清晰。”

### 7.11 TRAE 在项目中的作用

推荐回答：

“TRAE 不只是生成页面，而是参与了跨插件、前端、后端和测试的工程闭环：我们用它理解既有架构、迁移 Agent、补齐 WebSocket 与插件联调测试、定位会话 ID 和 React/D3 状态冲突，并持续把产品反馈落实成可验证改动。人的职责是确定产品边界、批准计划、复核风险和完成真实环境验收。”

### 7.12 当前最诚实的限制

推荐回答：

“当前最适合的是单机个人 Demo。模型延迟、第三方平台 DOM 变化、Service Worker 生命周期、本地配对鉴权、完整事务一致性和超大数据性能仍需继续加固。我们已经为关键失败提供提示和预置演示路径，但不会把预置结果冒充实时生成。”

## 8. 禁止夸大的口径

- 不说“所有对话都会自动建图”，应说“自动采集、智能抽取、用户确认入图”。
- 不说“所有问答都支持多轮”，应区分主 Chat 多轮能力与独立图谱 Q&A 的实际能力。
- 不说“实时行业风口”，应说“基于当前图谱的机会假设”。
- 不说“数据绝不离开本机”，应说明 LLM 请求会到用户配置的模型端点。
- 不说“企业级安全”或“可公网部署”，当前边界是 loopback 单机 Demo。
- 不说“六个平台永久稳定兼容”，应说明平台适配受第三方页面和协议变化影响。
- 不说“现场所有结果都是实时生成”，降级时必须明确标注为预先生成示例。

## 9. 最终验收清单

### 9.1 代码与测试

- 软件端前端完成 typecheck、lint、test、build；后端完成 ruff 与 pytest。
- 插件完成 `npm test` 与覆盖率检查，重点确认 Markdown 安全、Qdrant ID、Embedding `baseUrl` 和本地推送测试。
- 补齐或明确豁免 SQLite 并发、流式生命周期、WS 会话绑定、批量入图原子性和 FTS 生命周期测试。
- 确认工作区没有把截图、临时脚本、密钥、数据库或无关目录带入交付。

### 9.2 真实环境

- Chrome 真实扩展至少验证 DeepSeek、元宝和一个 Work 来源的采集、保存、推送、抽取、确认入图。
- Study 完整走通推荐理由、费曼题和反馈；Work 完整走通对象、承诺/风险关系和报告。
- LLM 离线、超时、取消和 WebSocket 重连均出现可理解的终态，不出现无限等待。
- 主题至少验证演示所用主题；窗口固定尺寸无横向滚动、遮挡或不可点击入口。

### 9.3 上台前

- 正常网络、慢网、断网各彩排 3 次，并记录每段实际耗时。
- 所有现场可见按钮都有真实结果；无法完成的入口在演示路径中隐藏或避开。
- 预置 Study/Work 数据、固定输入、扩展重载方法和刷新恢复路径均已准备。
- 最终画面停留在同时能看到来源、关系与行动结果的图谱或推荐卡片。
- 全程不打开 API Key、数据库文件、终端错误堆栈或开发者工具。
